# react-native-payments-example — e2e

The CI end-to-end tests for this package live in the repo root [`e2e/`](../../../e2e) project, under
[`e2e/tests/payments/`](../../../e2e/tests/payments): one `<flow>.e2e.ts` per scenario, with the shared steps in [`e2e/support/payments.ts`](../../../e2e/support/payments.ts). Every test targets the same file
regardless of app target (`apps/bare` / `apps/expo`) or platform (iOS / Android) — only the app id, the binary and the
leased device change; platform differences inside a test branch on `ctx.platform` rather than duplicated files. The
devices are leased from the simlock farm; no CI host boots a simulator or emulator.

## Layout

```
e2e/tests/payments/          one scenario per file, run in CI by the iOS E2E and Android E2E workflows
e2e/tests/payments-media/    google_pay_sheet.e2e.ts, the docs-media capture, never part of the assertion suite
e2e/support/payments.ts      shared steps (launch and wait for the probe, show, dismiss the iOS sheet)
```

`e2e/tests/payments-media/google_pay_sheet.e2e.ts` records the Google Pay loop (tap `action-show`, wait for Google Play
services to take the foreground, dismiss with back). The dispatch-only `docs-media.yml` workflow builds the bare APK,
runs the test on the farm's `android-gms` target (API 35 `google_apis`, with Google Play services), and turns
`recording/google-pay-sheet.mp4` into the `docs-media-payments` artifact (`google-pay-sheet.mp4` plus an
ffmpeg-converted GIF) for `packages/react-native-payments/docs/assets/`. The farm's emulator has no Google account, so
tapping `action-show` shows Google Play services' "Google Pay requires a Google account to be set up on this device."
dialog rather than a payment sheet.

## Running

```bash
cd e2e && npm ci
# @mobile-ci/e2e-simlock ships in mobile-ci, not on npm: install it from the tag the workflows pin, after every npm ci.
curl -fsSL https://raw.githubusercontent.com/rnw-community/mobile-ci/v4.11.1/scripts/fetch-e2e-simlock.sh | bash -s v4.11.1 .
SIMLOCK_URL=https://simlock.vitaliiyehorov.dev SIMLOCK_TOKEN=<token> E2E_TARGET=payments-bare \
  E2E_APP_ID=<target appId> E2E_APP_PATH=<built .app or .apk> npx e2e run --target ios   # or android
```

`E2E_TARGET` picks the suite: the CI target name minus its `-bare`/`-expo` suffix selects `e2e/tests/<suite>`. Build
the target app first (`ios:bare`, `android:bare`, `ios:expo`, `android:expo` from the package root, or the platform's
own tooling for the Expo native projects generated by `prebuild:expo`). A local run needs a simlock token for the farm.
On iOS the payments suite leases a full, unslimmed simulator, because the Apple Pay sheet needs PassKit.

## Waits are liveness bounds, not performance budgets

Every explicit wait here is sized for the slowest host the suite runs on, not for the transition it waits on.
Presenting and dismissing the PassKit sheet is the slowest thing the suite does, and slowest of all on whichever test runs
first against a just-installed app; an immediate assertion on the flow state after launch reports the state as missing
when it is merely not rendered yet. A tight timeout turns host contention into a red test that names a payment state
while payments are not what broke, so the launch allows 60s, the probe leaving `checking` 15s, the PassKit sheet's
`dismiss` element 120s (its first presentation has taken over a minute), and the post-dismiss state 45s. A generous
ceiling costs nothing when the assertion holds.

## Tests

Assertions read the on-screen event log (`event-log`, `event-log-count`, `event-log-row-<index>`)
and the `payments-flow-state` / `payments-can-make-status` labels documented in the package
`readme.md`'s `Test IDs` section. On iOS, six tests also assert briefly against the PassKit
sheet's own accessibility tree to dismiss it — see the documented gap below for why that step
exists and what it proves instead of a real payment authorization outcome.

## Google Play services on the CI emulator (Android)

CI runs the payments tests on the farm's API 34 `aosp_atd` emulator image (the `android` target in
`e2e/e2e.config.ts`), which has no Google Play services. The `PaymentsModule` availability guard described below
therefore fires on CI: `canMakePayment()`/`hasEnrolledInstrument()` resolve `false`. The Android branches never asserted
a Google Play services outcome — `can_make_payment_probe` only requires a terminal, non-crashing value — so they hold
unchanged. Tests still never assert that `show` settles on its own on Android. They force the settlement by tapping
`action-abort`: `PaymentRequest.abort()` rejects the pending `show()` promise with `AbortError` from the JS side whatever
the native task does, and if the native side rejected first, the state is already `rejected` and the abort degrades into
the already-closed no-op the `dismiss_abort_reject_state` iOS branch documents. The same forced settlement covers a device
that does have Google Play services but no Google account or provisioned card, where the outcome of `loadPaymentData`
belongs to Google Pay, not the app: it may reject on its own or stay pending indefinitely.

Historical context — CI once booted stock Redroid images, which are plain AOSP with no Google Play services at all.
Before `PaymentsModule` guarded against this, any GMS-dependent call — the mount-time `canMakePayment` probe
`usePaymentDemo`'s `useEffect` fires on every launch, and `action-show`'s `loadPaymentData` — logged
`GoogleApiAvailability: Google Play services is invalid. Cannot recover.` (`ConnectionResult.SERVICE_INVALID`, a generic
availability signal, not a statement that Payments specifically is unsupported), and Play services' own bundled fallback
UI turned that into a blocking system dialog ("… won't run without Google Play services, which are not supported by your
device.") over the whole screen, occluding `payments-flow-state` for every test.

`PaymentsModule.canMakePayments`/`hasEnrolledInstrument`/`show` now check
`GoogleApiAvailability.isGooglePlayServicesAvailable()` before the chained `isReadyToPay()`/`loadPaymentData()` call that
actually reaches into Play services — `Wallet.getPaymentsClient(...)` itself never fails on its own. On a device or
emulator without valid Play services, `canMakePayment()`/`hasEnrolledInstrument()` simply resolve `false` instead of
surfacing the dialog, the same outcome a real user would see on any Play-services-less Android device. The launch step
(`launchAndWaitForProbe`) and `showRequest` keep an optional Android "OK" dismissal as a defensive fallback, in case some
other GMS-backed path ever surfaces a similar dialog; it is a no-op once the native guard applies.

Separately (and unrelated to Play services): `event-log` and `event-log-count` sit below the fold on the 720x1280 @ 320dpi
Galaxy Nexus display CI leases, so tests scroll to them before asserting (`can_make_payment_probe`'s Android branch
scrolls to `event-log-count`). The Actions buttons straddle the same fold (`action-abort` partially visible,
`action-reset` fully below it), so tests scroll to them instead of asserting or tapping them in place, and scroll back up
before re-reading `payments-flow-state`, since after a downward scroll the status section is above the viewport.

## Documented gap: the PassKit sheet sandboxes the app's accessibility tree (iOS)

While a `PKPaymentAuthorizationController` sheet is presented, iOS blocks UI-test tooling (XCUITest, which agent-device
reads) from querying the hosting app's accessibility tree at all — the tree returns only the sheet's
own elements (`dismiss`, `pass`, `total`, …), none of the app's. The app itself behaves correctly the whole time —
`payments-flow-state` renders `showing`, `listeners attached` logs, the request eventually settles — but none of that is
_observable_ by the tests until the sheet closes. The sheet's own tree **is** reliably driveable (six tests use its
`dismiss` element to close it, via `dismissIosSheet`); it is the _app's_ tree that is unreachable for the sheet's
lifetime. Every iOS assertion that would target `payments-flow-state` or a log row **during** presentation targets the
sheet's `dismiss` element instead, then reads the app state **after** dismissal — the JS-observable half of the flow
moves to post-sheet, not away.

Android has no equivalent constraint: without Google Play services no sheet is presented at all, so the app's own
elements stay queryable throughout and the tests' Android branches are unaffected.

## Documented gap: native-sheet-driven completion

Two behaviors described in the package `readme.md` only fire from an event a **real, user-driven**
native sheet dispatches, which this suite cannot exercise on a simulator/emulator even after the
sheet-dismissal redesign above (dismissing the sheet is not the same as completing a payment
through it):

- the live shipping-address/option round trip (an actual `shippingaddresschange` /
  `shippingoptionchange` event carrying a user-picked address or option), and
- the `…updateWith started` / `…updateWith settled` log pair for **any** change event, including
  the async `updateWith` toggle exercised by `async_update_toggle_state` — that flow proves the
  toggle doesn't break request construction or listener attachment, but it cannot reach the
  `started`/`settled` rows themselves, because nothing dispatches a `paymentmethodchange` without a
  user interacting with the native sheet.

Both gaps share the same boundary: this suite covers the JS-observable half (request construction,
listener wiring, `show`/`abort`/`reset` state transitions, sheet presentation and dismissal), while
the library's unit tests cover payment authorization and `updateWith` completion itself. This is the
E2E depth documented on issue #393, not an oversight.
