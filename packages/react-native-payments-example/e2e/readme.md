# Maestro E2E suite

Shared, parameterized [Maestro](https://maestro.mobile.dev) flows that drive the demo screen in
`../src`. Every flow targets the same YAML regardless of app target (`apps/bare` / `apps/expo`) or
platform (iOS / Android) — only the `APP_ID` env value and the connected device change; platform
differences inside a flow are handled with Maestro's built-in `when: platform:` condition rather
than duplicated files.

## Layout

```
e2e/
├── flows/       one scenario per file, run directly by `maestro test`
└── subflows/    shared steps included via `runFlow`, never run standalone
```

## Running

```bash
yarn workspace @rnw-community/react-native-payments-example e2e:ios:bare
yarn workspace @rnw-community/react-native-payments-example e2e:ios:expo
yarn workspace @rnw-community/react-native-payments-example e2e:android:bare
yarn workspace @rnw-community/react-native-payments-example e2e:android:expo
```

Each script runs `maestro test -e APP_ID=<target appId> e2e/flows` against whichever
simulator/emulator is currently booted. Build and install the target app first (`ios:bare`,
`android:bare`, `ios:expo`, `android:expo` from the package root, or the platform's own tooling for
the Expo native projects generated by `prebuild:expo`).

| Target      | Platform | `APP_ID`                                                |
| ----------- | -------- | ------------------------------------------------------- |
| `apps/bare` | iOS      | `org.reactjs.native.example.ReactNativePaymentsExample` |
| `apps/bare` | Android  | `com.reactnativepaymentsexample`                        |
| `apps/expo` | iOS      | `com.reactnativepaymentsexpoexample`                    |
| `apps/expo` | Android  | `com.reactnativepaymentsexpoexample`                    |

## Waits are liveness bounds, not performance budgets

Every `extendedWaitUntil` here is sized for the slowest host the suite runs on, not for the transition it waits on.
Presenting and dismissing the PassKit sheet is the slowest thing the suite does, and slowest of all on whichever flow runs
first against a just-installed app; the launch subflow's flow-state check was a bare `assertVisible`, which allowed only
Maestro's short implicit retry and reported the state as missing when it was merely not rendered yet. A tight timeout turns
host contention into a red flow that names a payment state while payments are not what broke, so the launch allows 60s and
the sheet and post-dismiss state waits 45s. A generous ceiling costs nothing when the assertion holds.

## Flows

Assertions read the on-screen event log (`event-log`, `event-log-count`, `event-log-row-<index>`)
and the `payments-flow-state` / `payments-can-make-status` labels documented in the package
`readme.md`'s `Test IDs` section. On iOS, five flows also assert briefly against the PassKit
sheet's own accessibility tree to dismiss it — see the documented gap below for why that step
exists and what it proves instead of a real payment authorization outcome.

| Flow                                       | Proves                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app_launch.yaml`                          | The app launches, the four sections render, and the `canMakePayment` probe leaves `checking`.                                                                                                                                                                                                                                                                                                                                                                         |
| `can_make_payment_probe.yaml`              | iOS: `canMakePayment` resolves `available`. Android: it resolves to a terminal, non-crashing value.                                                                                                                                                                                                                                                                                                                                                                   |

| `async_update_toggle_state.yaml`           | Toggling async `updateWith` on does not change request construction or prevent `show` from attaching listeners — the JS-observable half of the async round trip (see the documented gap below for the half this suite cannot reach), read from the log after the iOS sheet dismisses.                                                                                                                                                                                 |

## Redroid has no Google Play Services (Android)

Redroid images are plain AOSP with no Google Play Services at all, unlike an AVD's `google_apis`
system image. Before `PaymentsModule` guarded against this, any GMS-dependent call — the
mount-time `canMakePayment` probe `usePaymentDemo`'s `useEffect` fires on every launch, and
`action-show`'s `loadPaymentData` — logged `GoogleApiAvailability: Google Play services is
invalid. Cannot recover.` (`ConnectionResult.SERVICE_INVALID`, a generic availability signal, not
a statement that Payments specifically is unsupported), and Play Services' own bundled fallback UI
turned that into a blocking system dialog ("… won't run without Google Play services, which are
not supported by your device.") over the whole screen. Since every flow routes through
`launch_and_wait_for_probe.yaml`, that dialog occluded `payments-flow-state` for all of them, not
just the flows that call `action-show`.

`PaymentsModule.canMakePayments`/`hasEnrolledInstrument`/`show` now check
`GoogleApiAvailability.isGooglePlayServicesAvailable()` before the chained
`isReadyToPay()`/`loadPaymentData()` call that actually reaches into Play services —
`Wallet.getPaymentsClient(...)` itself never fails on its own. On a device or emulator without
valid Play Services, `canMakePayment()`/`hasEnrolledInstrument()` now simply resolve `false`
instead of surfacing the dialog, the same outcome a real user would see on any Play-Services-less
Android device. `launch_and_wait_for_probe.yaml` keeps an `optional: true` "OK" dismissal on
Android as a defensive fallback — matching the pattern `subflows/show_request.yaml` already used
for the `action-show` tap — in case some other GMS-backed path this suite doesn't yet cover ever
surfaces a similar dialog; it is a no-op once the native guard applies.

Separately (and unrelated to Play Services): `launch_and_wait_for_probe.yaml` used to assert
`event-log` visible immediately after launch, and `can_make_payment_probe.yaml`'s Android branch
asserted `event-log-count` the same way. Both ids sit below the fold on Redroid's screen profile,
so neither is actually on-screen without scrolling first. The shared subflow's assertion was
dropped (redundant — flows that need `event-log`'s content already scroll to it themselves, e.g.
`app_launch.yaml`), and `can_make_payment_probe.yaml` gained a `scrollUntilVisible` ahead of its
own `event-log-count` assertion.

## Documented gap: the PassKit sheet sandboxes the app's accessibility tree (iOS)

While a `PKPaymentAuthorizationController` sheet is presented, iOS blocks UI-test tooling
(Maestro/XCUITest) from querying the hosting app's accessibility tree at all — `maestro hierarchy`
returns only the sheet's own elements (`dismiss`, `pass`, `total`, …), none of the app's. The app
itself behaves correctly the whole time — `payments-flow-state` renders `showing`, `listeners
attached` logs, the request eventually settles — but none of that is _observable_ by Maestro until
the sheet closes. This supersedes the previous phrasing ("the suite never depends on the native
sheet, which Maestro cannot reliably drive"): the sheet's own tree **is** reliably driveable (five
flows use its `dismiss` element to close it, via `subflows/dismiss_ios_sheet.yaml`), it is the
_app's_ tree that is unreachable for the sheet's lifetime. Every iOS assertion that used to target
`payments-flow-state` or a log row **during** presentation now targets the sheet's `dismiss`
element instead, then reads the app state **after** dismissal — the JS-observable half of the flow
moves to post-sheet, not away.

Android has no equivalent constraint: the Google Pay stub on the emulator never presents a real,
sandboxed sheet, so the app's own elements stay queryable throughout and the flows'
`when: platform: Android` branches are unaffected by this change.

## Documented gap: native-sheet-driven completion

Two behaviors described in the package `readme.md` only fire from an event a **real, user-driven**
native sheet dispatches, which this suite cannot exercise on a simulator/emulator even after the
sheet-dismissal redesign above (dismissing the sheet is not the same as completing a payment
through it):

- the live shipping-address/option round trip (an actual `shippingaddresschange` /
  `shippingoptionchange` event carrying a user-picked address or option), and
- the `…updateWith started` / `…updateWith settled` log pair for **any** change event, including
  the async `updateWith` toggle exercised by `async_update_toggle_state.yaml` — that flow proves the
  toggle doesn't break request construction or listener attachment, but it cannot reach the
  `started`/`settled` rows themselves, because nothing dispatches a `paymentmethodchange` without a
  user interacting with the native sheet.

Both gaps share the same boundary: this suite covers the JS-observable half (request construction,
listener wiring, `show`/`abort`/`reset` state transitions, sheet presentation and dismissal), while
the library's unit tests cover payment authorization and `updateWith` completion itself. This is the
E2E depth documented on issue #393, not an oversight.
