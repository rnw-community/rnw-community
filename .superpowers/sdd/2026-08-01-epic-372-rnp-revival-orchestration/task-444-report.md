## Addendum — canary follow-up fix (red screen / no embedded JS bundle)

The coordinator's first canary pass on this branch reported the fmt/Xcode wall was gone (app builds, installs, launches on the fleet) but every Maestro flow failed on the first assertion with the RN red screen: "No script URL provided ... unsanitizedScriptURLString = null". Root cause: `yarn ios:${{ matrix.target }}` / `yarn android:${{ matrix.target }}` in both workflows ran the CLI's default **Debug** configuration, whose `AppDelegate.swift`/`MainApplication.kt` always point at a Metro packager URL in Debug builds — and no packager runs on the headless CI fleet.

### Fix 1 — build self-contained Release apps (commit `f5abd0a9`)

- `ios-maestro.yml`: split the single "Build and launch app" step into per-target steps — `yarn ios:bare --mode Release --no-packager --extra-params "CODE_SIGNING_ALLOWED=NO"` and `yarn ios:expo --configuration Release --no-bundler` (the community CLI and the Expo CLI use different flag names for the same concepts: `--mode`/`--no-packager` vs `--configuration`/`--no-bundler`).
- `android-maestro.yml`: the single emulator-runner `script:` block now branches on `matrix.target` — `yarn android:bare --mode Release --no-packager` vs `yarn android:expo --variant release --no-bundler`.
- `CODE_SIGNING_ALLOWED=NO` only applies to the bare iOS leg (Expo's `run:ios` has no generic xcodebuild passthrough flag); verified locally that the regenerated `project.pbxproj` scopes `CODE_SIGN_IDENTITY` to `sdk=iphoneos*` only, with no `DEVELOPMENT_TEAM`/`CODE_SIGN_STYLE` set, so simulator builds already default to ad-hoc "Sign to Run Locally" regardless — the flag is defensive, not corrective.
- Android's `release` build type already signs with `signingConfigs.debug` (the standard bare-template default, `enableProguardInReleaseBuilds = false`), so no keystore/signing gap exists there.
- appIds are unchanged — Release doesn't add an `applicationIdSuffix` in this project's `build.gradle`, so `e2e:ios:*`/`e2e:android:*`'s hardcoded `APP_ID` values in `package.json` stay correct.

**Root-cause layer underneath the above**: verified locally that a plain `xcodebuild -configuration Release -sdk iphonesimulator build` for `apps/bare` failed independently of the Debug/Release CLI-flag question — the "Bundle React Native code and images" phase (confirming that phase *does* survive template regeneration, addressing the coordinator's stated concern) invoked Metro, which threw `TransformError [SyntaxError]: .../VirtualView.js: ';' expected (119:19)` on `match (mode) { ... }`. This is RN 0.86.2's own source using the newer Hermes/Flow `match` expression syntax, but the repo's root `package.json` had a treewide `resolutions.hermes-parser: "0.25.0"` override (pre-dating this PR, unrelated to RN 0.86) forcing every consumer — including `@react-native/metro-babel-transformer@0.86.2`, which natively wants `hermes-parser@0.36.1` — down to a parser two majors too old to read it. **Removed the `hermes-parser` resolution entirely**; each consumer now resolves its own natural version (older RN 0.76-era consumers still get `0.25.x`/`0.25.1` as before, since that's what *they* declare — nothing broke for `platform`/`fast-style`). Re-ran the full gate suite (`build && ts && lint && test && deadcode`, plus `react-native-payments` `test:coverage`) after the resolutions change — still all green, coverage still 100/100/100/100.

Re-verified locally after the fix: `xcodebuild -configuration Release -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build` for `apps/bare` — **BUILD SUCCEEDED**, and `main.jsbundle` (2.4 MB) is now present inside the built `.app`, confirming the embedded-bundle path works end-to-end.

### Fix 2 — expo target never built the payments config plugin (commit `acc74a3e`)

While corroborating the failure against the actual failed run logs (`gh run view 30738369162 --log-failed`), found the `expo` matrix leg was failing even earlier than the coordinator's red-screen report describes — at "Generate native project (expo)" — with:
```
PluginError: Failed to resolve plugin for module "@rnw-community/react-native-payments/app.plugin" relative to ".../apps/expo". Do you have node modules installed?
```
`react-native-payments`'s `package.json` `exports["./app.plugin"]` only maps to `dist/esm/app.plugin.js` / `dist/cjs/app.plugin.js` — there is no `src` fallback — and neither workflow ever ran `yarn build` before `expo prebuild`/`yarn prebuild:expo`, so on a clean CI checkout `dist/` never exists and Node's `exports`-aware resolution fails outright, before Maestro or Metro ever enter the picture. Reproduced locally by deleting `packages/react-native-payments/dist` and running `expo config --type prebuild` (same `PluginError`), then confirmed `yarn build --filter=@rnw-community/react-native-payments` (a scoped, cache-friendly turbo filter — resolves `shared` first, then the payments package) fixes it. Added a `Build react-native-payments (expo)` step, gated `if: matrix.target == 'expo'`, immediately before each workflow's `Generate native project (expo)` step.

Both workflow-only edits passed `actionlint .github/workflows/ios-maestro.yml .github/workflows/android-maestro.yml` with zero findings.

## Round 3 — genuine e2e territory: PassKit sheet blocks accessibility tree

Round 3 (commit `94e89d6f`) reached real end-to-end behavior on the expo iOS leg for the first time: `app_launch` and `can_make_payment_probe` **passed**. Diagnosed the remaining failures with direct evidence — local reproduction on this machine's own Xcode 26.3 + Maestro 2.6.1, not just log archaeology — before deciding what to fix vs. document.

### Bare iOS leg regression — confirmed infra bug, fixed

`gh run view 30740994533 --log-failed` showed `Build app (bare)` failing at the "Bundle React Native code and images" phase with a Metro `resolveDependency` error:
```
originModulePath: '.../packages/react-native-payments-example/src/hook/use-payment-demo.ts',
targetModuleName: '@rnw-community/shared'
packageJsonPath: '.../node_modules/@rnw-community/shared/package.json',
mainModulePath: '.../node_modules/@rnw-community/shared/dist/cjs/index.js',
```
Root cause: unlike `@rnw-community/react-native-payments` (whose `package.json` `"react-native"` field points Metro straight at `src/index.ts`, needing no build step), `@rnw-community/shared` has no such field, so Metro falls back to `"main"` → `dist/cjs/index.js`. The round-2 workflow only ran the `yarn build --filter=@rnw-community/react-native-payments` step (which transitively builds `shared` too) `if: matrix.target == 'expo'` — the bare leg never built anything, so on a clean CI checkout `packages/shared/dist/` never existed. Locally reproduced by confirming `packages/shared/dist/cjs/index.js` only existed on this machine because an earlier round's testing had built it — a genuinely fresh checkout would hit the identical failure Metro reported. **Fix** (commit `952195ba`): dropped the `if: matrix.target == 'expo'` condition — the build step now runs unconditionally in both workflows, renamed to "Build workspace JS dependencies" since it's no longer expo-specific.

### Expo iOS leg — real e2e findings, verified by local reproduction

To evaluate the coordinator's three hypotheses with real evidence rather than more log-reading, reproduced the flows directly on this machine: booted a local simulator (Xcode 26.3), built `apps/bare` Release (`apps/bare` shares 100% of `src/` with `apps/expo` — same JS logic, only native scaffolding differs, and `apps/expo`'s own local build is blocked by the unrelated `expo-modules-jsi` Swift-ambiguity bug documented in round 1, so `apps/bare` was the reproducible proxy), installed it, and ran the actual failing flow with `maestro test -e APP_ID=org.reactjs.native.example.ReactNativePaymentsExample e2e/flows/sheet_opens_on_show.yaml`.

**Reproduced exactly**: `Assertion is false: "showing", id: payments-flow-state is visible` — the identical failure signature from the fleet run.

Maestro's own failure screenshot (`~/.maestro/tests/.../screenshot-❌-...png`) showed the real **Apple Pay sheet already presented** on top of the app — "Simulated Card - Visa •••• 1234", shipping method "Standard / Free", "Pay Total 20,00 US$", actively "Processing" — and, visible in the sliver of app UI still on-screen above the sheet, the app's own `flow` label already read **"showing"**. The state transition and the PassKit sheet presentation both happened correctly. Dumping the live accessibility tree while the sheet was up (`maestro hierarchy`) confirmed why the assertion still failed: **the tree contained only the PassKit sheet's own native elements** (`"Simulated Card - Visa, •••• 1234"` etc.) — zero elements from the app underneath, no `payments-flow-state`, no `action-abort`, nothing. A follow-up manual relaunch (without clearing state) showed the request eventually **auto-settles to `rejected`** with a full 5-entry event log including `listeners attached: ...` — confirming that step logs correctly too, it simply isn't visible to Maestro while the sheet is up, and by the time the sheet dismisses and the tree becomes queryable again, `flowState` has already moved past `"showing"` to `"rejected"`, so there is no timing window in which `"showing"` is both true and observable.

**Conclusion, with the coordinator's three hypotheses addressed directly:**

1. **`sheet_opens_on_show` / `async_update_toggle_state`** (flow-state never "showing"): **not a rejection, not a presentation failure, not a library or app defect.** The sheet presents correctly with a valid simulated card and the JS state transitions correctly; the assertion fails because iOS's native `PKPaymentAuthorizationController` sheet is a system-owned, security-sandboxed surface that XCUITest (and therefore Maestro on iOS) cannot see through or past — the underlying app's accessibility tree is entirely unreachable for the sheet's whole lifetime. This is a hard OS-level constraint on the flow's *design*, not a bug anywhere in `react-native-payments`, the demo app, or this PR's changes.
2. **`shipping_listener_wiring_*`** (expected "listeners attached" text not found): the coordinator's `couponcodechange` hypothesis is **disproven by the source** — `defaultRequestOptions.coupon` is `false`, and neither `shipping_listener_wiring_enabled.yaml` nor `_disabled.yaml` toggles the coupon control, so `attachChangeListeners`'s `options.coupon && Platform.OS === 'ios'` branch never fires in this scenario; the expected `paymentmethodchange,shippingaddresschange,shippingoptionchange` list is platform-invariant here. The real cause is the same as #1: `attachChangeListeners` runs and logs the line correctly (confirmed in the manual repro's event log) *before* `show()` even opens the sheet, but `show_request.yaml`'s `tapOn: action-show` immediately triggers the same sheet presentation, and the subsequent `scrollUntilVisible` for that log text loses the same accessibility-tree race.
3. **`dismiss_abort_reject_state` / `reset_new_request_state_transitions`** (`action-abort` not found): same root cause again, not a separate, downstream-only symptom in a strict causal sense — every flow that calls `show_request.yaml` and then queries *any* app element immediately afterward hits the identical PassKit-sheet-blocks-accessibility wall.

**Disposition**: this is **not** being filed as a `react-native-payments` library issue — the payment flow works. It is a `maestro-e2e` flow-design gap: the suite's own `e2e/readme.md` already documents that "the suite never depends on the native Apple Pay / Google Pay sheet itself, which Maestro cannot reliably drive," but `sheet_opens_on_show.yaml`'s iOS branch (and the three flows chained after `show_request.yaml`) accidentally *do* require querying app state while that sheet is the frontmost surface. A correct fix needs a verified interaction pattern for iOS specifically (e.g., confirming whether the sheet can be dismissed/cancelled from outside, or restructuring assertions to only check log state *before* the sheet opens or *after* it settles, accepting that `"showing"` itself is unobservable) and was **not attempted on this branch** — the original issue #444 explicitly scoped "Maestro flows/appIds unchanged," this is a deeper, unproven flow-design question requiring its own iteration and verification budget rather than a same-session guess that could burn further canary cycles without confidence, and Android's equivalent behavior (where these same flows already passed in earlier framing, since Google Pay isn't configured on the emulator and no real sheet ever blocks the tree) suggests the fix is iOS-specific flow branching, not a platform-agnostic tweak.

## Follow-up: issue #449 — iOS flow redesign (separate branch/PR)

PR #446 merged to master (issue #444 closed). Coordinator opened a dedicated follow-up, issue #449, to fix the PassKit-sheet-accessibility-sandbox finding documented above. Implemented on a new branch off current `origin/master` (containing the #446 merge): `feat/rnp-449-ios-flow-redesign`, PR #450.

### Root-cause confirmation, with the exact dismiss mechanism found

Rebuilt `apps/bare` locally (Release, `-derivedDataPath build`, `CODE_SIGNING_ALLOWED=NO`), reproduced the sheet-blocks-accessibility finding again, then dumped the **full** `maestro hierarchy` JSON (not just a grep) while the PassKit sheet was presented. It contains a complete, structured tree of the sheet's own native elements, including:
```
text='Close' id='dismiss' bounds=[325,335][368,378] enabled=true
```
alongside `pass` (the simulated card), `change-method`, `shipping-address`, `shipping-method`, `total` (`Pay Total, 20,00 US$`), and `footer` (`Processing`). Tapping `id: "dismiss"` immediately closes the sheet and settles the request:
```
event-log-row-4: show rejected: error=[ReactNativePayments] [DOMException]: The operation was aborted.
```
Tapping `action-abort` afterward (now reachable, since the app's tree is unblocked again) produces:
```
event-log-row-5: abort called: id=...
event-log-row-6: abort rejected: error=[ReactNativePayments] [DOMException]: The object is in an invalid state.
```
— a distinct, meaningful rejection (not a crash, not a silent no-op), confirming `abort()` on an already-non-interactive request correctly surfaces an invalid-state error per the W3C Payment Request spec's semantics.

Also directly disproved the earlier `couponcodechange` hypothesis with hierarchy evidence (not just source reading this time): the post-dismissal event log's `listeners attached` row reads exactly `types=paymentmethodchange,shippingaddresschange,shippingoptionchange` — the same list `shipping_listener_wiring_enabled.yaml` already expected, confirming the coupon toggle was never the issue.

### Redesign approach

Added `e2e/subflows/dismiss_ios_sheet.yaml` — internally gated `when: platform: iOS` (so callers can `runFlow` it unconditionally and it's a no-op on Android) — that asserts the sheet's `dismiss` element, taps it, and waits for `payments-flow-state` to reach `rejected`. Routed it into all five affected flows immediately after `show_request.yaml`, moving every app-state/event-log assertion that used to run *during* sheet presentation to run *after* dismissal instead:

- `sheet_opens_on_show.yaml` — dismiss, then assert `show called` (shared step, unchanged) plus a new iOS-only block mirroring the pre-existing Android block's final assertions (`show rejected` logged, `action-reset` visible) — the Android block itself is untouched byte-for-byte.
- `async_update_toggle_state.yaml`, `shipping_listener_wiring_enabled.yaml`, `shipping_listener_wiring_disabled.yaml` — dismiss, then read the log (these flows had no explicit Android branch to begin with; Android was already unaffected since its stub never blocks the tree).
- `dismiss_abort_reject_state.yaml` — dismiss first, *then* tap `action-abort` on the settled request (previously it tapped `action-abort` while the sheet was interactive, which is no longer reachable on iOS) — still asserts `abort called`, which logs regardless of the resolve/reject outcome, so the assertion stays accurate for both platforms even though the underlying JS path now differs (Android: abort succeeds on an interactive request; iOS: abort rejects on an already-settled one).
- `reset_new_request_state_transitions.yaml` — the previously-unconditional `action-abort` tap is now wrapped `when: platform: Android` (iOS reaches `rejected` via sheet dismissal instead, at the same point in the sequence); the flow's final iOS assertion changed from asserting `payments-flow-state: showing` (unobservable) to asserting the sheet's `dismiss` element is visible again, proving `action-reset` genuinely rebuilds a fresh, interactive request rather than reusing a closed one.

`e2e/readme.md`'s documented-gap section was rewritten: the old phrasing ("the suite never depends on the native sheet, which Maestro cannot reliably drive") is corrected — the sheet's own tree **is** reliably driveable (that's exactly how dismissal works now); the real, precise boundary is that the **app's** tree is unreadable for the sheet's lifetime. Added a dedicated subsection describing the sandbox and the flow-design pattern used to work around it, and clarified that the pre-existing native-sheet-driven-completion gap (shipping address/option round trip, `updateWith` started/settled log pairs) is a *separate*, still-open gap — dismissing a sheet immediately is not the same as completing a payment through user interaction with it.
